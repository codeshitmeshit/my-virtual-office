# 会议人工决策讨论轮回写设计

日期：2026-08-08

## 目标

用户完成会议中的人工决策后，VO 必须把最终决策作为一条独立、权威的会议事件写回触发决策的原讨论轮。会议界面通过既有 SSE 实时展示该记录，后续会议 Agent 的 Prompt 也必须读取该记录，从而继续执行已确认的结论，并避免针对同一问题重复发起决策。

本功能只改变会议人工决策的事件投影与上下文消费，不改变聊天、项目续跑语义，也不把人工决策伪装成 AI 参会者发言。

## 已确认的产品行为

1. 讨论轮内显示一条独立的“👤 人工决策”记录。
2. 记录只展示决策标题、最终结果和非空的自定义补充。
3. ABCD 全部备选项与 VO 推荐不在讨论轮展开，用户可通过“查看决策详情”进入现有决策中枢查看。
4. 决策记录属于触发该决策的原始讨论阶段和轮次，而不是恢复执行后的新轮次。
5. 后续所有会议 Agent 都能从会议历史上下文读取最终决策，并被明确要求不得针对同一问题重复发起人工决策。
6. 决策记录不计入参会者发言数、正式轮次完成条件或主持人收敛统计。
7. 飞书或 VO 控制面板完成决策后均写入同一权威事件；现有 SSE 负责实时同步，不新增第二条实时通道。

## 方案选择

### 采用：扩展既有 `human_decision_resolved` 事件

会议生命周期已经在决策恢复时创建 `human_decision_resolved` 事件。本次扩展该事件的稳定载荷，并将它投影到会议记录和 Agent Prompt。该方案保留了“用户决策”和“AI 发言”的语义边界，也能复用既有会议事件、SSE 和幂等能力。

### 不采用：合成 `participant_turn`

把决策伪装成参会者发言可以复用部分 UI，但会污染参会者发言数和轮次完成判定，还会错误表达事件主体，因此不采用。

### 不采用：仅追加到下一次 Prompt

只向下一次 Prompt 注入文本无法在会议历史中审计，页面也不会实时展示；上下文压缩后还可能丢失结论，因此不采用。

## 权威事件模型

`human_decision_resolved` 继续作为唯一权威事件类型。事件必须带有以下投影字段：

```json
{
  "type": "human_decision_resolved",
  "stage": "<decisionForStage>",
  "round": 2,
  "payload": {
    "decisionId": "decision-...",
    "title": "确认保留期与合同例外策略",
    "answer": "第一版默认保留 7 天",
    "customAnswer": "企业租户允许在合同白名单内延长至 14 天"
  }
}
```

- `stage` 和 `round` 取自会议在进入等待状态时保存的 `decisionForStage` 与 `decisionForRound`。
- `answer` 是决策中枢规范化后的最终答案；自定义输入优先时，`answer` 仍是后续执行消费的权威文本。
- `customAnswer` 仅在用户确实填写自定义补充时保存和展示；空值不渲染。
- `decisionId` 同时作为详情跳转参数和幂等身份的一部分。
- 事件沿用 `human-decision-resume:{decisionId}` 幂等键，重复回调、恢复扫描或 SSE 重连不得产生重复记录。

## 后端组件边界

新增聚焦模块 `app/services/meeting_human_decision_projection.py`，负责把已解决决策与会议等待快照规范化为事件载荷和 Agent 可读文本。该模块不导入 `app/server.py`，只消费显式传入的 meeting、resolution 和 decision metadata。

会议生命周期继续拥有状态转换和事件追加权威：

1. `HumanDecisionMeetingContinuation` 读取统一决策终态，并将决策标题、自定义补充和规范化答案传给会议 `continue_decision` 转移。
2. `MeetingLifecycleService` 在确认当前 decision ID 匹配后，调用投影模块构造 `human_decision_resolved` 载荷，并通过既有事件追加钩子原子持久化。
3. 兼容入口不得复制业务规则；如仍经过 legacy transition，应薄委托到同一生命周期服务或同一投影函数。
4. `app/server.py` 只保留依赖装配与调用委托，不新增事件拼装逻辑。

## 会议历史与 Prompt 投影

会议转录投影新增 `human_decision_resolved` 类型，保留原始 `stage`、`round`、`decisionId`、`title`、`answer` 和可选 `customAnswer`。

会议历史文本生成器把该事件格式化为明确的权威上下文，例如：

```text
[人工决策已完成][decision-123] 确认保留期与合同例外策略：第一版默认保留 7 天；补充：企业租户允许在合同白名单内延长至 14 天。后续不得就同一问题重复发起决策。
```

该文本作为动态、不可信会议数据进入共享 XML Prompt formatter 的数据边界。系统规则继续位于可信 XML 元素中；不得通过字符串拼接把用户答案放入指令层。

## 前端展示与 SSE

`app/meetings-ui.js` 的会议实时事件投影识别 `human_decision_resolved`，并按事件携带的原始 `stage + round` 插入对应讨论轮。

UI 使用独立的人工决策样式，不复用 Codex、Claude Code 等 Agent 身份：

- 标题行：`👤 人工决策`；
- 主体：决策标题和最终结果；
- 补充：只在 `customAnswer` 非空且未与最终结果重复时显示；
- 操作：`查看决策详情`，打开现有人工决策中枢并定位 `decisionId`；
- 时间：沿用会议事件时间；
- 排序：沿用讨论轮内现有事件时间顺序。

初始化加载、SSE 增量到达和 SSE 重连都使用同一投影与去重逻辑。新增文案必须接入现有中英文 i18n 字典，不写死中文。

## 状态与错误处理

- 找不到 `decisionForRound` 时，优先使用决策创建事件保存的轮次；仍无法定位时挂到 `decisionForStage` 的当前轮，并记录诊断信息，不丢弃权威事件。
- 会议已被其他操作推进但同一决策已应用时，按幂等成功处理并复用已有事件。
- decision ID 不匹配、会议已终止或恢复目标不兼容时，不追加伪造的完成事件；续跑维持既有失败分类。
- UI 无法打开详情时仍保留决策文本，详情入口失败不得影响会议记录展示。
- 旧会议没有该事件时保持原有展示，不做历史数据推测或迁移。

## 测试策略

1. 生命周期测试：决策完成事件绑定原 `decisionForStage + decisionForRound`，载荷包含标题、最终答案和可选自定义补充。
2. 幂等测试：重复 `continue_decision`、恢复扫描和相同 SSE 事件只保留一条记录。
3. Prompt 测试：后续 Agent 历史包含权威决策文本和“不重复决策”约束；恶意答案不能闭合可信 XML 标签。
4. 转录投影测试：API 输出保留人工决策类型及详情字段。
5. UI 测试：初始化与 SSE 都把记录渲染到原讨论轮；空自定义补充不显示；详情入口携带正确 decision ID。
6. 轮次回归：人工决策记录不计入 participant turn、正式轮次完成条件或主持人收敛统计。
7. 集成验证：本地创建包含真实议题和多 Agent 发言的会议，触发人工决策，提交后确认讨论轮实时出现记录，并确认下一位 Agent 的输入包含该结论。

## 非目标

- 不在讨论轮展开完整 ABCD 备选项或 VO 推荐说明。
- 不改变决策中枢详情页、飞书卡片或提醒策略。
- 不新增会议 SSE 通道或第二套会议历史存储。
- 不把人工决策算作参会 Agent 发言。
- 不回填缺少权威事件的历史会议。
