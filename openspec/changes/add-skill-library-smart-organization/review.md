## 评审结论

**带条件通过。**

方案复用现有档案管理员、management token 和活动日志，未引入新的外部依赖，也没有给 Skill 增加整理生命周期字段。进入实现前，任务清单必须把共享防重、原子目录元数据、严格 AI 输出校验、启动恢复和管理权限测试列为独立可验证工作。

## 阻塞问题

无。

## 主要风险

### 稳定性

- 档案室现有三个 `working` 入口没有共享原子防重，若只检查 JSON 状态仍存在并发竞态。
- 后台整理进程异常退出可能留下持久化 running 展示。

### 数据一致性

- Skill 文件夹可被 UI 外部直接增删，目录与分类 sidecar 必须持续对账。
- AI 整理与人工分类可能同时修改相同 Skill，必须通过协调器和 catalog revision 双重保护。

### 安全

- `SKILL.md` 内容是不可信输入，可能包含诱导档案管理员执行指令的文本。
- 所有整理及分类写接口必须在读取请求体前通过 management token 校验。

### 性能

- 默认分类数量增长时，全量提示会扩大模型输入和请求时长。
- 前端轮询必须仅在运行期间启用，避免常驻请求。

### 兼容性

- 当前 `/api/skills-library` 返回结构已被旧 UI 和测试使用；新增字段必须保持 `skills` 数组兼容。
- sidecar 必须作为隐藏普通文件，不能被现有目录扫描误认为 Skill。

### 可回滚性

- 需求明确不支持用户级撤销，因此技术回滚只能停止新任务并保留或备份分类元数据。
- 新代码关闭后不得影响 `SKILL.md` CRUD 和向 Agent 应用 Skill。

### 可观测性

- 只有顶部标记与一条终态活动日志，服务端仍需提供脱敏的 run ID、耗时和计数日志支持排障。
- 不得按每个 Skill 输出高频日志或记录原始 Skill 内容与模型回复。

## 关键追问

### Q1：为什么不把分类写入 SKILL.md？

A：SKILL.md 是可移植指令源，分类属于 Virtual Office 本地治理元数据。写入 frontmatter 会混淆内容所有权并制造同步差异，因此使用原子 sidecar。

### Q2：为什么需要进程锁，检查 `manager.json.status` 不够吗？

A：两个并发请求可能同时读到 idle。非阻塞进程锁负责原子准入，manager.json 只负责跨 UI 展示和恢复信息。

### Q3：为什么使用后台 worker 而不是同步 HTTP？

A：现有档案管理员调用可能持续数分钟。`202 + runId + 有界轮询` 可以展示运行状态、允许页面刷新，并避免长连接承担任务生命周期。

### Q4：为什么不增加持久队列？

A：产品明确要求忙碌时按钮置灰且不排队。单进程、单任务协调器满足当前容量，同时减少恢复和重复消费复杂度。

### Q5：怎样保证部分失败不会覆盖人工修改？

A：每个 AI 结果只能作用于本次快照中的 slug；提交前重新检查该 Skill 仍存在且仍在默认分类，并要求人工写携带 catalog revision。

### Q6：怎样防止 Skill 内容提示注入？

A：只发送名称、描述、frontmatter 和标题摘要，明确声明为不可信数据；模型只能返回 JSON，服务端对 slug、分类和标签做白名单与长度校验。

### Q7：档案管理员不存在或暂停时怎么办？

A：整理直接返回稳定错误，不自动创建或替换 Agent。暂停状态也视为不可执行，保持现有管理员治理权。

### Q8：为什么活动日志只有一条终态记录？

A：运行中状态由 manager 当前状态表达；终态活动记录满足追溯需求，并符合产品不建设详细技能整理反馈的约束。

## 测试与上线建议

- Catalog：首次投影、系统分类不可变、外部增删对账、revision 冲突、原子写失败、损坏 JSON、symlink 拒绝。
- 权限：所有新增 POST 在读取 body 前拒绝缺失或错误的 management token；合法 owner 请求通过。
- 防重：技能整理分别与手动档案整理、AI 精整、档案数检查并发，后到请求稳定返回 busy，且没有排队执行。
- AI 合约：正常、未知 slug、重复 slug、漏项、非法分类、超长标签、路径值、非 JSON、超时和提示注入样例。
- 部分失败：成功项移动、失败项留默认、失败过滤、逐项人工修正、计数递减及最终 resolved。
- 恢复：进程在 running 后重启，旧 run 变为 interrupted/failed，manager 不再永久 busy。
- 兼容：旧 `skills` 消费者、创建、导入、save-from-agent、apply、删除及 MCP Registry 独立入口回归。
- UI：忙碌与空默认按钮禁用、顶部 marker 留存/关闭/替换、无 team-space 文案、无 MCP 浏览入口。
- 容量：至少 100 个默认 Skill 的多批次运行，验证批次上限、单并发、日志数量和轮询停止。
- 上线：先以开关关闭部署，完成本地 acceptance 后启用；观察 run 耗时、失败率、busy 拒绝数和 catalog 写错误，再决定默认开启。
- 回滚门禁：关闭开关后不得启动新 run；技能 CRUD/apply 必须继续可用；sidecar 备份和恢复步骤必须验证。
