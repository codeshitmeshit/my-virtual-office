## ADDED Requirements

### Requirement: VO 控制面板固定决策入口
人工决策中枢 SHALL 面向 VO 控制面板提供固定入口，并在入口上展示当前待决策数量和关注状态。

#### Scenario: 普通新决策到达
- **WHEN** 新增一个不属于高风险且未临近超时的待决策事项
- **THEN** 入口徽标更新待决策数量，但中枢不自动打开

#### Scenario: 高风险决策到达
- **WHEN** 新增一个高风险待决策事项
- **THEN** 中枢自动打开并聚焦该事项，同时入口保持准确的待决策数量

#### Scenario: 决策即将超时
- **WHEN** 一个待决策事项进入临近超时状态
- **THEN** 中枢自动打开并聚焦该事项，清楚展示剩余时间和超时后果

### Requirement: 轻量决策收件箱
人工决策中枢 SHALL 提供待决策列表、选中事项详情和已处理历史，不在本期提供搜索、统计或批量管理。

#### Scenario: 用户打开中枢
- **WHEN** 用户点击控制面板固定入口
- **THEN** 中枢展示全部待决策事项，并在没有既有选择时聚焦最需要关注的事项

#### Scenario: 用户切换待决策事项
- **WHEN** 用户在待决策列表选择另一事项
- **THEN** 详情区域展示该事项唯一对应的完整决策卡

#### Scenario: 用户查看已处理历史
- **WHEN** 用户切换到已处理历史
- **THEN** 中枢展示最终决策、处理方式、处理时间和 VO 后续动作，且历史项不可再次作为未处理事项提交

### Requirement: 决策情景与任务上下文
决策详情 SHALL 展示来源场景、当前情景、决策原因、风险等级、超时后果以及默认折叠的任务详细信息。

#### Scenario: 用户查看决策摘要
- **WHEN** 用户选中一个待决策事项
- **THEN** 详情同时呈现任务、会议或聊天来源，情景摘要、决策原因、风险等级和超时后果

#### Scenario: 用户展开任务详情
- **WHEN** 用户展开默认折叠的详细信息
- **THEN** 详情展示任务摘要、已完成进展、当前阻塞、相关上下文和决策后的下一步

### Requirement: ABCD、VO 推荐与自定义答案
决策详情 SHALL 展示 A、B、C、D 四个真实候选项及各项影响，其中一个 MUST 标记为 VO 推荐项并说明理由。详情 SHALL 同时提供自定义答案输入和明确的提交操作。

#### Scenario: 用户选择候选项
- **WHEN** 用户只选择 A、B、C、D 中任一项
- **THEN** 提交采用所选候选项作为最终决策

#### Scenario: 用户填写自定义答案
- **WHEN** 用户填写有效自定义答案，无论是否同时选择候选项
- **THEN** 提交采用自定义答案作为最终决策，已选候选项仅作为参考

#### Scenario: 用户没有提供答案
- **WHEN** 用户未选择候选项且未填写有效自定义答案
- **THEN** 中枢拒绝提交并就近提示必须提供一种答案

### Requirement: 提醒与超时结果
决策详情 SHALL 展示基于紧急程度的提醒节奏、下一次提醒时间和最多三次提醒的进度。

#### Scenario: 决策仍在提醒周期
- **WHEN** 决策尚未达到第三次提醒
- **THEN** 详情展示当前提醒次数、总次数、紧急程度和下一提醒时间

#### Scenario: 低风险决策三次提醒后超时
- **WHEN** 低风险决策在第三次提醒后仍未响应
- **THEN** 中枢展示已按 VO 推荐项继续，并标明这是超时自动处理而非用户主动选择

#### Scenario: 高风险决策三次提醒后超时
- **WHEN** 高风险决策在第三次提醒后仍未响应
- **THEN** 中枢展示受影响任务分支继续等待，并说明其他明确且安全的工作可以继续

### Requirement: 提交反馈与修改边界
用户提交后，决策详情 SHALL 展示最终决策、提交时间和 VO 下一步动作。VO 开始执行前 SHALL 允许修改；开始执行后原决策 SHALL 锁定。

#### Scenario: 用户提交决策
- **WHEN** 用户成功提交
- **THEN** 该事项从待决策队列移入已处理历史，并展示最终决策、提交时间、同步语义和下一步动作

#### Scenario: 执行开始前修改
- **WHEN** 用户在 VO 尚未开始执行时选择修改
- **THEN** 中枢恢复该事项的可编辑状态并允许重新提交

#### Scenario: 执行开始后请求改变
- **WHEN** 用户对已锁定决策发起变更
- **THEN** 中枢先展示潜在影响和不可逆边界，并在用户再次确认后报告变更请求

### Requirement: 双端镜像语义
中枢 SHALL 表达同一请求同时存在于飞书和本地 UI、任一端提交后两端均成为已处理的产品语义。本期展览 MUST 使用示例状态表达，不得声称已完成真实同步。

#### Scenario: 请求尚未处理
- **WHEN** 同一请求尚未从任一入口提交
- **THEN** 详情显示飞书与本地 UI 均为等待状态

#### Scenario: 请求已从任一入口处理
- **WHEN** 示例状态表示用户已从飞书或本地 UI 提交
- **THEN** 中枢展示唯一最终决策，并将两个入口均表达为已处理

### Requirement: 外部处理结果实时协调
中枢组件 SHALL 接受带单调版本号的完整决策快照，并在无需刷新页面的情况下协调徽标、待决策队列、当前详情和已处理历史。正式控制面板集成 SHALL 复用现有 Dashboard SSE 的 `decisions` 分区；本期展览页 SHALL 模拟同一快照契约。

#### Scenario: 飞书处理结果到达 VO
- **WHEN** 用户已在飞书处理一个待决策事项，且中枢收到包含该结果的更新版本快照
- **THEN** 待决策徽标立即减少，该事项从待决策队列迁移到已处理历史，详情展示唯一最终答案、飞书处理入口、处理时间和 VO 下一步动作

#### Scenario: 用户正在查看被飞书处理的事项
- **WHEN** 更新版本快照把当前选中的待决策事项标记为已处理
- **THEN** 中枢清除未提交的本地草稿和重复提交能力，并将当前详情切换为该事项的只读最终结果

#### Scenario: 重复或过期快照到达
- **WHEN** 中枢收到 revision 等于或早于当前 revision 的决策快照
- **THEN** 中枢忽略该快照，不得把已处理事项回滚为待决策或恢复旧草稿

#### Scenario: 正式控制面板接收实时更新
- **WHEN** 后续正式集成从现有 `/api/dashboard/events` 收到 `decisions` 快照或差量事件
- **THEN** Dashboard 实时模块更新 `dashboard.decisions` 并调用中枢更新接口，不创建额外的 EventSource、WebSocket 或轮询循环

#### Scenario: 展览页模拟飞书处理
- **WHEN** 验收人员在临时展览页触发“飞书已处理”示例状态
- **THEN** 展览页通过模拟 `dashboard.decisions` 的更新版本快照驱动相同的队列迁移和只读结果展示，且不连接真实 SSE 或飞书服务

### Requirement: 响应式中枢体验
中枢 SHALL 在桌面宽度使用列表和详情双栏布局，在窄屏宽度使用列表/详情单视图切换，核心流程不得依赖横向滚动。

#### Scenario: 桌面查看中枢
- **WHEN** 中枢在桌面视口打开
- **THEN** 待决策列表和选中事项详情同时可见

#### Scenario: 窄屏查看中枢
- **WHEN** 中枢在窄屏视口打开
- **THEN** 用户先查看列表，选择事项后进入详情，并可通过明确操作返回列表

### Requirement: 中枢组件与临时展览宿主分离
系统 SHALL 将入口提醒、列表、详情、历史和交互规则实现为可嵌入 VO 控制面板的独立组件。临时 HTML 展览页 MUST 仅模拟控制面板、注入示例数据和挂载组件。

#### Scenario: 本地展览完整中枢
- **WHEN** 验收人员打开临时本地 HTML
- **THEN** 可以查看普通徽标、高风险自动打开、队列、历史及全部决策生命周期，无需后端或外部平台

#### Scenario: UI 确认后删除展览宿主
- **WHEN** 删除临时 HTML 及示例控制器
- **THEN** 中枢组件、组件样式和组件契约测试仍独立保留，可供正式 VO 控制面板集成

#### Scenario: 用户操作展览页
- **WHEN** 用户切换状态、选择事项、填写答案或提交示例决策
- **THEN** 所有变化仅存在于展览范围，不发送机器人消息、不写生产数据、不改变真实任务状态且不触发 VO 执行动作

### Requirement: 统一决策状态权威
系统 SHALL 以持久化服务作为本地 UI 与飞书的唯一决策状态权威，并以单调 revision 输出完整安全快照。

#### Scenario: 两个入口竞争提交
- **WHEN** 本地 UI 与飞书先后提交同一待决策事项
- **THEN** 首个有效提交成为唯一终态；相同重试幂等成功，不同答案返回稳定冲突且不得覆盖终态

#### Scenario: 自定义答案与候选项同时提交
- **WHEN** 请求同时包含 A-D 候选项和非空自定义答案
- **THEN** 权威状态采用自定义答案作为最终决策

### Requirement: 正式控制面板实时集成
正式 VO 控制面板 SHALL 通过现有 `/api/dashboard/events` 的 `decisions` 分区驱动决策中枢，并提供同源 REST 降级快照。

#### Scenario: 飞书回调完成决策
- **WHEN** 飞书回调写入更高 revision 的已处理状态
- **THEN** 现有 Dashboard SSE 推送 `dashboard.decisions`，本地弹窗无需刷新即移入历史且入口徽标减少

#### Scenario: SSE 暂时不可用
- **WHEN** Dashboard 实时连接失败并进入现有 fetch 降级
- **THEN** 前端通过决策快照 API 获取相同安全投影，不新建轮询器或第二条实时连接

### Requirement: 飞书决策卡片
系统 SHALL 优先通过已配置的通知机器人发送包含情景、任务详情、ABCD、自定义输入和提交动作的飞书卡片；通知机器人未配置时 SHALL 降级到聊天机器人配置的回退会话。

#### Scenario: 通知机器人已配置
- **WHEN** 创建一个有效决策请求且通知机器人应用配置完整
- **THEN** 卡片只发送给通知机器人目标，不同时发送给聊天机器人

#### Scenario: 通知机器人未配置
- **WHEN** 通知机器人配置不完整但聊天机器人及回退会话可用
- **THEN** 系统使用聊天机器人向回退会话发送同一决策卡片

#### Scenario: 飞书提交决策
- **WHEN** 用户在飞书提交 A-D 或自定义答案
- **THEN** 回调写入统一状态权威，自定义答案优先，并把原卡片更新为不可重复提交的终态摘要

### Requirement: 跨执行场景的决策 Skill
系统 SHALL 提供一个可由任务、会议和聊天执行共同调用的人工决策 Skill；Skill 只在 VO 无法安全代决且选择会实质影响结果时创建请求。

#### Scenario: 执行器需要人工裁决
- **WHEN** 任务、会议或聊天执行器识别到多个合理选项且无权自行选择
- **THEN** Skill 创建带 ABCD、推荐项、上下文和超时策略的决策请求，并只暂停受影响分支

#### Scenario: 未受影响工作可继续
- **WHEN** 决策请求仍处于待处理状态
- **THEN** Skill 明确允许其他独立且安全的执行分支继续运行

### Requirement: 执行 Prompt 主动升级重大未授权取舍
系统 SHALL 在聊天、会议和项目执行 Prompt 中注入同一套人工决策升级规则：Agent 先通过工具、证据、既定规则和历史授权消除普通不确定性；若仍存在多个实质不同的合理方案，且选择影响结果、风险、范围、成本或不可逆动作，同时 Agent 无权或置信度不足以代决，则 SHALL 使用人工决策 Skill，而不是静默选择或仅以普通聊天提问。

#### Scenario: 执行中仍有重大未授权选择
- **WHEN** 聊天、会议或项目 Agent 调查后仍面对多个实质不同的方案，且没有用户授权或足够置信度代决
- **THEN** Prompt 要求 Agent 使用 `vo-human-decision` 创建对应 `chat`、`meeting` 或 `task` 来源的决策请求，只暂停受影响分支

#### Scenario: 普通执行不确定性可自行验证
- **WHEN** 问题可通过继续读取、测试或执行唯一安全且可逆的操作解决
- **THEN** Prompt 要求 Agent 继续自主处理，不创建人工决策请求

### Requirement: 聊天决策完成后后端自动续跑
系统 SHALL 在聊天来源的人工决策首次形成有效终态后，由后端自动唤醒创建该请求的原 Agent，并在原 conversation 中携带最终答案继续暂停分支；该能力 SHALL 不依赖 VO 页面保持打开。

#### Scenario: 本地或飞书完成聊天决策
- **WHEN** `source.type=chat` 的决策从本地控制面板或飞书首次写入有效终态
- **THEN** 后端使用创建请求时可信绑定的 Agent ID 与 `source.id` 对应的原 conversation 投递一次续跑输入，并把回复写回原聊天历史

#### Scenario: 页面关闭或服务重启
- **WHEN** 用户提交决策时 VO 页面未打开，或服务在终态写入后、Provider 投递前重启
- **THEN** 持久化续跑任务仍处于可恢复状态，并由启动或周期处理继续领取

#### Scenario: 重复回调或重复扫描
- **WHEN** 相同终态被重复回调、幂等提交或定时扫描观察到
- **THEN** 同一决策不得产生第二次 Provider 续跑

#### Scenario: 明确未投递的临时失败
- **WHEN** 原 conversation 正忙或 Provider 在调用前明确不可用
- **THEN** 后端最多重试三次，并使用持久化的有界退避状态

#### Scenario: 投递结果不确定
- **WHEN** Provider 可能已接收续跑输入但后端失去明确结果
- **THEN** 续跑状态标记为 `uncertain`，不得盲目自动重试

#### Scenario: 非聊天来源完成决策
- **WHEN** `source.type` 为 `meeting` 或 `task`
- **THEN** 系统保持对应执行器现有生命周期，不调用聊天续跑器，并由对应原生适配器自动恢复受影响分支

### Requirement: 会议决策完成后原生续跑
系统 SHALL 在会议来源决策形成终态后，通过既有会议生命周期的 `continue_decision` 恢复原会议，并复用既有会议事件、运行器和 Dashboard SSE。

#### Scenario: 会议决策完成
- **WHEN** 绑定同一 decision 的会议仍处于 `awaiting_user_decision`
- **THEN** 后端幂等记录最终答案，执行一次 `continue_decision` 并唤醒原会议运行器

#### Scenario: 会议已被其他操作推进
- **WHEN** 会议已终止或不再等待该 decision
- **THEN** 后端不得倒退会议阶段或创建普通聊天续跑

### Requirement: 项目任务决策完成后单分支续跑
系统 SHALL 在项目 task attempt 等待人工决策时保留其活动 attempt；决策完成后 SHALL 复用原 attempt/session 并只重新提交该 task，不暂停或重投同 stage 的兄弟任务。

#### Scenario: 项目执行器创建决策
- **WHEN** 活动 task attempt 创建绑定的人工决策并结束当前 Provider turn
- **THEN** attempt 保持 `awaiting_user_decision` 非终态，项目不得进入 Review、完成或提前推进 stage

#### Scenario: 用户完成项目任务决策
- **WHEN** 绑定的项目任务决策首次形成有效终态
- **THEN** 后端将答案作为 XML 不可信数据注入原 attempt，复用既有 runner/dispatcher 只恢复该 task

#### Scenario: 同阶段存在其他任务
- **WHEN** 一个 task 等待或恢复人工决策且同 stage 还有其他活动 task
- **THEN** 其他 task 的 active attempt 和调度状态保持不变
